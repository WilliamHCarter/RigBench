# v0.3.1 — extensibility addendum

Benchmark plumbing and parameterization for the sweeps that come next. **No
tuning policy.** The harness gains the ability to express, record and compare
every axis; it acquires no opinion about which values are good, and none of
MQ4/PM4/block/KV/adaptive appears anywhere as a default or a recommendation.

The split this implements: the harness owns *expressing* the knobs; deciding
which combinations to run and what the results mean stays outside.

## Audit against the eight requirements

| # | Requirement | Before | Now |
|---|---|---|---|
| 1 | Engine config exposes the tuning axes | quant/KV/speculation as loose strings; the rest absent | `knobs` block, 25 named axes plus `extra` |
| 2 | Speculative internals in telemetry | τ, acceptance, block | plus windows, accepted, rejected, draft TPS, verify TPS/ms, KV format, resolved model — and `serve.log` ingestion |
| 3 | Workload outcome separate from engine performance | one flat struct | `story.inference` and `story.task` |
| 4 | Per-turn generation budgets | one global `max_tokens` | `turn_limits: {initial, repair, final}` |
| 5 | Experiment metadata | absent | `experiment: {family, variant, baseline}`, grouped in the report |
| 6 | GPU affinity / replica identity | absent | `knobs.gpu`, `knobs.gpu_env`, `knobs.replica_id`, `knobs.concurrency` |
| 7 | Prompt-cache telemetry per turn | hit/miss tokens, prefix **bytes** | three-way accounting per turn, in tokens, with a verdict |
| 8 | Artifact provenance | model/draft hash if pasted into a config | requested vs resolved model, file paths, SHA-256 computed by the harness |

## 7 first, since it is the one that could not be retrofitted

Three different numbers get called "the cache hit" and they are not the same
measurement. All three are now recorded, per turn:

- **`reusable_prefix_tokens`** — what the *prompt* makes reusable, measured by
  the runner from the bytes it serialized. Engine-independent, available against
  a backend that reports nothing, and the only one comparable across engines.
- **`shared_with_previous_tokens`** — what this turn shares with the previous
  turn of the same story. In a multi-turn loop this is the number that actually
  predicts prefill work.
- **`cached_tokens`** — what the *engine* says it reused. Ground truth when
  exposed, null when not.

Plus `newly_prefilled_tokens` and `reuse_fraction`, derived **only** when both
sides were reported — mixing a server counter with a client heuristic produces a
number belonging to neither. And a `verdict`: `full` / `partial` / `miss` /
`not-exposed`, so a backend that reported nothing never renders as one that
reused nothing.

A live run now shows:

```
| Turn | Role    | Cap  | Prompt tok  | Reusable prefix | Shared w/ prev | Appended | Cached      | Verdict     |
| 0    | initial | 8192 | not exposed | 10017           | 0              | 10133    | not exposed | not-exposed |
| 1    | repair  | 4096 | not exposed | 10017           | 10133          | 1323     | not exposed | not-exposed |
```

The reusable prefix is constant while the shared prefix grows — the shape the
design rule predicts.

### A bug this found

Turn 0 initially reported sharing 10,133 tokens with a turn that does not exist,
because the previous manifest was overwritten before the comparison. Every story
would have looked cache-friendly from its first request. Fixed, extracted into a
pure `turnReuse`, and pinned by `TestTurnZeroSharesNothing`.

## 3 — inference and task are separate groups

`story.json` now has two:

```
inference:  model_wall_ms, prefill/decode/draft/verify TPS, TTFTs, tau,
            acceptance, windows, accepted, rejected, token totals, cache
            verdicts, finish reasons, knob fingerprint, resolved model, GPU
task:       success, stop_reason, turns, patch_attempts, failed_applies,
            tool/model/total wall, time_to_first_compiling_patch,
            time_to_discriminating_green, time_to_hidden_green
```

Rates are medians and counts are totals: a rate averaged over turns of very
different lengths is dominated by the shortest.

This is not presentational. A configuration decoded ~5% faster, generated 2.1×
more output and failed the task; on any blended score it would have looked
competitive. `TestTaskSuccessIsIndependentOfInferenceSpeed` pins the separation.

A backend with **no** telemetry produces an `inference` group full of nulls and a
**complete** `task` group — the right shape, since workload outcome does not
depend on the engine being instrumented.

## 2 — server-log ingestion

The line that was being grepped out of `serve.log` by hand is now read by the
harness:

```
drafter=dflash tau=4.86 tok/s=32.9 windows=5593 accepted=27184 rejected=5584 kv=q8
```

`-server-log <path>` marks the file's end before each request and reads only what
appeared after, so telemetry is attributed to the request that produced it rather
than to the session. The raw slice is kept as a per-turn artifact. Verified end to
end: `windows=5593 accepted=27184 rejected=5584 kv_obs=q8`.

Design notes that matter:

- **An unknown key is ignored, not guessed at.** A wrong mapping fabricates a
  number, which is the one outcome the telemetry layer exists to prevent.
- **Acceptance is normalized** — `0.426` and `42.6%` both become `0.426`, so a
  server that changes representation between releases cannot move a column by two
  orders of magnitude.
- **Rotation is survived** rather than leaving the reader seeked past a new
  file's end, silently returning nothing forever.
- Stream telemetry is preferred over log telemetry and the log fills gaps;
  neither overwrites the other.

## 1, 6 — knobs as data, applied by the hook

25 named axes: target/draft model, quant, file and SHA-256; KV dtype;
speculation method, block, budget, adaptive; verify mode and PM4; prefill
speculation; prompt-cache mode and capacity (with a **required** unit, because a
bare number that might be tokens, megabytes or sequences is not a measurement);
context and max-output tokens; concurrency, replica id, GPU and GPU env. Plus
`extra` for any axis not yet named, so a new knob never blocks on a harness
change.

None are sent on the request — they are process-level settings on every local
engine worth benchmarking. They reach the server as `AGENTBENCH_KNOB_*`
environment variables on the preparation hook. **An unset knob is absent, not
empty**, so a hook can tell "leave it alone" from "set it to nothing".

`prepare-hipfire.sh` now applies them, and **fails loudly on a knob it cannot
map**:

```
WARNING: unmapped knob AGENTBENCH_KNOB_MYSTERY -- requested but NOT applied
FATAL: 1 requested knob(s) have no mapping here.
```

Silently dropping a requested knob would produce a row labelled with a setting
the server never had — the same failure class as the v0.2.1 engine-identity bug.

`knob_fingerprint` is a stable one-line summary on every row: two rows with the
same fingerprint asked the server for the same thing.

## 4 — per-turn budgets

```json
"turn_limits": { "initial": 8192, "repair": 4096, "final": 2048 }
```

Role by position: turn 0 is initial, the last permitted turn is final, the rest
are repair. Zero falls back to the engine's `max_tokens`, so a lane that does not
care keeps working. `final` with no value falls back to `repair`, not to the
engine default — which would silently give the last turn the *largest* ceiling.

Each row records `turn_role`, `turn_max_tokens` and the engine's own
`finish_reason`, so a truncated answer is attributable to the ceiling that caused
it. `finish_reasons` is counted per story: a story whose turns all hit `length`
is a different result from one whose turns all `stop`, however similar the wall
clock.

## 5 — experiment metadata

```json
"experiment": { "family": "speculation", "variant": "dflash2-f16", "baseline": "ar" }
```

Recorded on every row and in `run.json`; the summary groups by family. Metadata,
never logic — the benchmark does not decide what to sweep, it only lets a sweep
name itself. The table leads with the Green column, with the reason stated
underneath.

## 8 — artifact provenance

`run.json` now separates `requested_model` from `resolved_model`, and carries
`target_file` / `target_sha256` / `draft_file` / `draft_sha256`. Where the file is
readable from the host, **the harness computes the digest** rather than trusting
one pasted into a config: the paste is a snapshot of what was true when somebody
last looked. Where it is not readable — the usual case for a remote rig — the
declared value stands and is recorded as declared.

This is the `fast` → `mq4-xt` alias problem, moved out of shell notes.

## What was deliberately not built

- **No optimization policy.** No MQ4/MQ6 recommendation, no PM4 default, no
  block value, no KV choice, no adaptive speculation. Those are hypotheses to
  test from outside.
- **No automatic optimizer.** The objective landscape is not understood well
  enough. A config-driven matrix runner is useful later; "find the best settings"
  is not.
- **No new sweeps run.** The rig configs carry knob *declarations* only, matching
  what is already there: AR with speculation off, DFlash2 with an F16 drafter.

## Still unmeasured

- **The Hipfire config keys in the hook are still guesses** — `dflash_block`,
  `dflash_budget`, `verify_pm4`, `prompt_cache`, `context_length`. Step 0 of the
  [runbook](rig-campaign.md) now covers them too. A wrong key name will surface
  as a `hipfire config set` failure rather than as a silently wrong row.
- **The `serve.log` key names are guesses.** Unknown keys are ignored, so a wrong
  guess yields null rather than a fabricated number, but the mapping needs
  confirming against a real log.
- **`prompt_tokens` per turn is only as good as the engine's usage block.** The
  runner's own counts remain estimates from `approx-runs-v1` until the v0.5
  tokenizer lands.
- **No real inference.** All of this is verified against the in-repo mock.
- `verify-fixture` has still never been run on the rig, and its toolchain is
  still unresolved.
