# v0.3 — live builder repair loop

**Goal.** Measure seconds per successful coding task when the model can edit, run
tests, observe failures, and repair its work.

The one-shot experiment is closed. Its finding was not "Qwen failed" — it was
that the bottleneck is the agent loop rather than token throughput, and that a
patch which compiles is not a patch that implements anything. This slice
measures the loop.

## What changed from v0.2

v0.2's replay was **exogenous**: assistant turns and tool results were fixture
bytes, so every engine received identical prompts and prefix behaviour could be
isolated. v0.3 is **endogenous** — the model's own output becomes the next
prompt.

That buys realism and costs cross-engine prompt equality. Two engines running a
live lane legitimately diverge at turn 1, so the prompt-hash equality check is
disabled for live lanes and the summary says why. What survives is the
append-only property *within* one story, still asserted before every request.

## The two lanes

| | `builder-live` | `builder-repair-diagnostic` |
|---|---|---|
| Feedback | visible build/test output only | plus the hidden suite's real failure after turn 0 |
| Hidden suite | run **once**, after the loop stops | leaked after turn 0, then run again at the end |
| Max turns | 6 | 3 |
| Purpose | the benchmark | characterizing repair capability |

The diagnostic lane answers *"given exact evidence, can this model wire what it
left unwired"* — not *"can this model succeed from ordinary feedback"*. Its
stories carry `hidden_leaked_after_turn` and the summary marks the lane
**(diagnostic)**. They are never comparable with `builder-live`.

Note the framing correction from [v0.2.3](v0.2.3.md): the AR one-shot result was
not a near miss. It produced a patch that compiled and did not implement the
seam. So the diagnostic lane is measuring recovery from *nothing wired*, not
recovery from *nearly right*.

## The integrity property

If the hidden suite is in the tree while the loop runs, `zig build test`
compiles it, its failures reach the model through the tool output, and the
benchmark is grading a model on evidence it handed over.

So the acceptance gate scans **every prompt of every turn** for content unique to
the hidden suite:

```
live-converges   on builder-live               leak=false
live-stuck       on builder-live               leak=false
live-no-diff     on builder-live               leak=false
live-immediate-done on builder-live            leak=false
live-converges   on builder-repair-diagnostic  leak=true
```

The last row is the negative control. Without it, a leak check that never fires
would pass forever whether or not the mechanism worked.

## The interaction contract

Live turns use their own agent contract
(`public/agent_contract_live.md`), which the lane selects — the story, doctrine
and source context are the same bytes as the one-shot lane, so the lanes stay
comparable on prompt shape.

It asks for **only** a fenced diff, no analysis before it, no repeated unchanged
files, and at most five lines of note afterwards. This attacks the behaviour the
rig measured directly: 15,309 completion tokens for AR and 32,768 for DFlash,
much of it narration before the artifact. `DONE` on its own line ends the loop.

A model declaring `DONE` does not make the story green. The host still runs the
hidden suite, and the `live-immediate-done` acceptance row pins that.

## Scoring

```
total_wall = Σ model request wall + Σ patch apply + build + test time
```

Decomposed rather than totalled, because *the model is slow*, *the model needed
four more turns* and *the build is slow* are three different problems with three
different fixes, and one number hides which you have.

`story.json` records, per story: `model_wall_ms`, `tool_wall_ms`,
`total_wall_ms`, `model_turns`, `patch_attempts`, `failed_apply_attempts`,
`no_diff_turns`, `completion_tokens_total`, `reasoning_tokens_total`,
`time_to_first_compiling_patch_ms`, `time_to_discriminating_green_ms`,
`time_to_hidden_green_ms`, `stop_reason`, and the per-turn gate sets.

**The north-star metric is the median seconds to a hidden-green story**, and the
summary leads with it. Medians cover green stories only: a story that failed fast
is not a fast story, and averaging it in would reward giving up.

### `time_to_visible_green` is not a metric here

The peer's spec asked for it. It would have measured nothing —
[v0.2.3](v0.2.3.md) showed a one-line comment patch passes the visible suite. It
is `time_to_discriminating_green`: the first turn at which the visible rung
**and** the candidate-test discrimination gate both pass.

## Stop reasons

A story that ran out of turns and one that finished are not the same result, so
the reason is recorded and asserted:

| Reason | Meaning |
|---|---|
| `model declared done` | the model returned `DONE` |
| `visible rung and discrimination gate both green` | the host stopped it; a model that never declares completion would otherwise burn its budget on a finished tree |
| `turn budget exhausted` | `max_turns` |
| `wall-clock budget exhausted` | `max_wall_seconds` |
| `the model returned no diff twice in a row` | prose with no artifact |
| `transport failure` | retained as a measurement, never retried into green |

## Tool output is sanitized at runtime

A build log carries the absolute worktree path, the toolchain cache, runtime
addresses and durations. Leaving them in makes the prompt host-dependent: two
engines on one rig would receive different bytes and the prompt hash would move
every run — a harness problem that looks like an engine problem.

v0.2's trajectory was sanitized once by hand when frozen. A live loop generates
its tool output at runtime, so `executor.Sanitize` does it per turn, and
`TruncateMiddle` caps it at the lane's `max_tool_output_bytes` keeping head and
tail with an explicit elision marker. Real agents truncate, and an untruncated
failing build can exceed the context window — which would end a run for a reason
that has nothing to do with the model.

`live-converges` reproduces the rig's shape deliberately: turn 0 lands the new
files and wires nothing — which builds and passes the visible suite, exactly like
the one-shot AR result — and turn 1 repairs it once the host reports the
discrimination failure. Turn 0's discrimination gate is asserted to fail, or the
fixture would not be reproducing the failure this lane exists to study.

## Bug found while building this

**The scope gate reported 30 out-of-scope files that no candidate wrote.** The
live worktree is built in place and persists across turns, so `zig build` left
`.zig-cache/` behind and `git status` counted it. The one-shot path never hit
this because its scope check ran before the build.

Fixed by writing `.git/info/exclude` when staging — not a `.gitignore` in the
tree, which would be a fixture byte the candidate could see, diff against, and be
blamed for.

## Not measured

- **No real inference.** Every number here is the in-repo mock replaying a
  scripted candidate. The loop's *mechanics* are verified; nothing about any
  model's repair capability is.
- **The scripted candidate converges by construction.** `live-converges` proves
  the harness can observe a repair, not that any model can produce one.
- **Harness overhead outside model and tool time is excluded** from
  `total_wall_ms` and is not measured.
- **Turn-level output quality is not judged.** A turn is scored by what its diff
  did to the tree, not by whether its reasoning was sound.
- **The `DONE` sentinel is a fixture convention.** A model that ends its work
  some other way will exhaust its turn budget instead, which is recorded as a
  different stop reason but scored the same.
- Everything unmeasured in [v0.1](v0.1.md), [v0.2](v0.2.md),
  [v0.2.1](v0.2.1.md), [v0.2.2](v0.2.2.md) and [v0.2.3](v0.2.3.md) remains so —
  in particular, `verify-fixture` has still never been run on the rig, and its
  toolchain is unresolved.

## The campaign this enables

Not "can DFlash finish the same 32K monologue faster". The question is:

> can it reduce total wall across a successful two-to-four turn builder
> trajectory without hurting repair success?

Keep F16 DFlash unchanged. No MQ6/MQ4 drafts, no adaptive block, no PM4, no KV
mode changes until there is a successful live trajectory to optimize against.

```bash
go run ./cmd/agentbench run -lane builder-live -before-engine ./scripts/prepare-hipfire.sh -engines configs/engines/ar.json,configs/engines/dflash2.json -endpoint http://127.0.0.1:11435/v1 -thermal steady -warmup 1 -repeats 3
```

Then the diagnostic lane, whose result is the interesting one given that the
one-shot patch wired nothing:

```bash
go run ./cmd/agentbench run -lane builder-repair-diagnostic -before-engine ./scripts/prepare-hipfire.sh -engines configs/engines/ar.json,configs/engines/dflash2.json -endpoint http://127.0.0.1:11435/v1 -thermal steady -warmup 1 -repeats 3
```
