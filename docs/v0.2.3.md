# v0.2.3 — the gate stack could not detect an empty patch

The first rig campaign produced an AR one-shot result read as a near miss:

```
patch extracted ✓   patch applies ✓   scope ✓   build ✓   visible tests ✓   hidden tests ✗
```

That reading does not survive contact with a control. **A 397-byte patch that
adds one comment line and changes nothing else produces the identical gate
signature.**

```diff
+// The active flag.
 pub const flag_active: u32 = 1 << 0;
```

```
patch_extracted  pass
patch_applies    pass
scope            pass
build            pass
visible_tests    pass
hidden_tests     FAIL
return_contract  pass
```

Six of seven gates for doing nothing.

## Why

The visible suite ships with the frozen HEAD and tests **only behaviour that
existed before the seam**. It cannot test `FrameRange` or `Tone`, because at
HEAD they do not exist. So `build` and `visible_tests` are satisfied by any
patch that compiles, including one that implements nothing.

The hidden failures from the campaign say exactly this: 24 compile errors, all
of the form `Cold` has no field `range`, `Cold` has no field `tone`,
`root.zig` has no member `FrameRange`, `cursor.advance` still takes two
arguments. The seam was never wired. The result is much closer to the new
`unwired` control than to a near miss.

The irony is pointed. The fixture carries twelve mutants proving the *hidden*
suite is not vacuous, and a tripwire proving each hidden file actually executes.
Nothing was proving the same of the gates above them.

## The gate that discriminates

`candidate_tests_discriminate` replays only the candidate's own **test** files
against the frozen HEAD, without the candidate's implementation, and requires
them to go red.

The story asks the builder to write invariant-named tests. If those tests still
pass against a tree where the seam does not exist, they do not defend the
invariants they are named after — and neither does the visible rung that ran
them. A patch that adds no test file at all fails by definition.

It is the same question the fixture asks everywhere else — *would this fail if
the body under test were emptied?* — turned on the candidate. What it does not
prove is that the tests are **correct**; the hidden suite still owns that.

Measured against every control:

| Candidate | build | visible | discriminate | hidden |
|---|---|---|---|---|
| `reference` | pass | pass | **pass** — 4 test files go red at HEAD | pass |
| `visible-green-hidden-red` | pass | pass | **pass** | fail |
| `unwired` — new files, wired into nothing | pass | pass | **fail** — no test file | fail |
| `comment-only` — one comment line | pass | pass | **fail** — no test file | fail |

`unwired` and `comment-only` are now permanent rows in the acceptance table, so
the gate stack has controls of its own. 16 rows, 0 mismatches.

## Consequences for the campaign conclusions

- **The DFlash conclusion is untouched.** 32,768 completion tokens against AR's
  15,309, no usable patch, ~2.02× worse wall for ~5% better decode — that is
  independent evidence and it stands.
- **The AR conclusion needs restating.** Not "AR reached compile/visible-green
  and needs test feedback", but "AR produced a patch that compiles and does not
  implement the seam, and the gate stack could not tell." Whether AR is close is
  now an open question rather than a finding.
- **`time_to_visible_green` was going to be a meaningless metric** in the v0.3
  live loop, for the same reason. It needs to be `time_to_discriminating_green`
  or dropped.

## Two fixes from the rig branch, and what they exposed

`rigbench-runfix-001` carried two real fixes. Both are merged; one needed
replacing rather than adopting.

### The hex formatting fix pointed at a bigger problem

The branch changed the Player golden's hex rendering to
`std.fmt.fmtSliceHexLower(&d)`. That is correct on Zig 0.14 and **does not
exist on Zig 0.16**, which is what `build.zig.zon` pins and what the fixture was
verified under. The original `{x}` over a pointer-to-array is correct on 0.16
and wrong on 0.14. Neither is portable.

So the rig ran a campaign under **Zig 0.14** against a fixture whose goldens,
twelve mutant controls and hidden suite were all verified under **0.16**, and
nothing in the run said so.

Both halves are fixed:

- `digestHex` no longer routes through `std.fmt` at all. Sixteen characters of
  lookup table produce the same bytes on every release. A frozen golden's
  textual form must not depend on a formatting verb whose behaviour changes
  between compilers. The digest is unchanged, so no golden was re-blessed.
- `fixture.json` gained `toolchain.zig`, and it is now **checked** rather than
  recorded. An exact mismatch refuses the run:

```
fixture zig-playback-v1 was verified under zig 0.16.0 but zig 0.14.1 will run here.
Its goldens, its twelve mutant controls and its hidden suite are evidence only
under the compiler that produced them, and results from two compilers are not
comparable.
```

`-allow-toolchain-drift` proceeds and attaches the mismatch as a caveat on every
row. `minimum_zig_version` remains what it says — a minimum for the package
manager — while `toolchain.zig` is the exact pin the benchmark enforces.

### The health-model fix applies to the engine configs too

The branch split `AGENTBENCH_HEALTH_MODEL` from the serve alias because
`/health` reports a different model name than the name used to serve.

The shipped engine configs had the same guess baked into
`identity_probe.require.model`, where it would have aborted every run. Those
`require` blocks are now empty, carrying a note pointing at step 0 of the
runbook, and an empty `require` no longer counts as verification:

```
prepared by hook; the probe recorded the server's answer but asserted
nothing about it (identity_probe.require is empty)
```

`Attested` is now true only when something was actually checked. Asking is not
attesting.

## What the rig should re-run before trusting the fixture there

`agentbench verify-fixture` has never been run on `willy1`. The twelve mutant
controls and the four tripwires are the evidence that the hidden suite is not
vacuous, and that evidence was produced under 0.16 on a different machine. Under
0.14 it is unverified. Either install 0.16.0, or run `verify-fixture` under 0.14
and, if all twelve controls still hold, set `toolchain.zig` to that version
deliberately.
